## Cluster topology and node-lifecycle assumptions (ADR-033, ADR-034, ADR-035)

| # | Assumption | Status | Evidence / risk if false |
|---|---|---|---|
| A-N1 | Default initial shard count of `max(min(3 × node_count_at_creation, 64), 3)` gives day-one multi-leader distribution while bounding Raft-group overhead. | **Accepted (risk)** | The 3× multiplier is a starting point picked to give every node ~3 shards on average. The 64 cap is a soft limit chosen because each shard = 1 Raft group; 64 groups per cluster is well-tested in similar systems (Ceph PGs scale higher, but with batched heartbeats kiseki-raft does not yet support). If kiseki-raft adds Multi-Raft-style heartbeat batching, the cap can be raised. If the 3× starting ratio proves too sparse for typical workloads, the cluster admin may raise the multiplier without spec change. |
| A-N2 | Ratio floor of 1.5× is sufficient to avoid stranding nodes idle when one shard is hot. | **Accepted (risk)** | At ratio 1.5, every node hosts on average 1.5 shards; even if one shard is hot enough to dominate a single node's resources, every other node has at least one alternative leader. Below 1.5 (e.g., 1.0), a single hot shard can monopolize a node. The floor is cluster-admin configurable; if observed workloads need higher headroom, raise it. |
| A-N3 | Best-effort round-robin leader placement at creation/split/merge is sufficient for steady-state balance; explicit periodic rebalance is not required for correctness. | **Accepted (risk)** | No invariant enforces post-hoc balance. Drift between events is permitted. If observed drift consistently strands nodes, an explicit rebalance ADR may follow. Operators have a manual rebalance lever (out of scope for ADR-033). |
| A-N4 | The drain-refusal-at-RF-floor policy (I-N4) is the correct safety stance — refusing the drain is preferable to allowing temporary RF<3 with alarms. | **Validated** | Confirmed by domain expert 2026-04-25 (Q1=a). Trades operator inconvenience for durability invariant preservation; aligned with I-CS1 (CP for writes) and the regulatory threat model A-E4. |
| A-N5 | Threshold ownership: cluster admin sets cluster-wide split/merge defaults and per-tenant min/max envelopes; tenant admin may override per namespace within the envelope. | **Validated** | Confirmed by analyst inference 2026-04-25 (resolves prior open escalation #2). Prevents one tenant from saturating Raft-group budget; tenant admin retains tuning control for their workloads' characteristics. |
| A-N6 | The merge interval default of 24 hours is long enough to avoid thrash from transient utilization dips but short enough to reclaim Raft-group overhead within an operationally acceptable window. | **Accepted (risk)** | Tunable per cluster admin. If observed workloads have day-cycle utilization patterns (e.g., quiet overnight, busy during day), the interval may need raising to a multiple of 24 h to avoid daily merge/split oscillation. |
| A-N7 | Drain cancellation (I-N7) is operationally desirable and does not compromise correctness — completed voter replacements are not rolled back, which is the simplest safe behavior. | **Validated** | Architect confirmed 2026-04-25 in ADR-035 §4. Rollback would require removing the new voter and re-adding the old one, risking a window where RF < 3. The completed replacements are valid placements; the cluster operates correctly. Operator can use explicit voter management to rebalance later. |

## Native gateway data service assumptions (ADR-042 — in design)

Captured during analyst diamond cycle 2026-05-05. `**Validated**` = confirmed by domain expert during interrogation; `**Accepted (risk)**` = inferred or acknowledged risk.

| # | Assumption | Status | Evidence / risk if false |
|---|---|---|---|
| A-NG1 | The native gateway data service exposes both *object-flavored* and *POSIX-flavored* verb families. FUSE will eventually move to the POSIX-flavored surface (replacing today's `KisekiFuse → RemoteHttpGateway` HTTP path); the migration is its own follow-up work-stream after ADR-042 lands the protocol. | **Validated** | Domain expert 2026-05-05 (Q1 = both). Both surfaces share auth, audit, and tenant model. Risk if false: native and FUSE diverge into two separate protocols, doubling spec and implementation surface. |
| A-NG2 | Tenant identity on native ops is bound by *both* the mTLS cert SAN URI *and* the request payload `tenant_id`, validated to match at the proto-handler boundary. | **Validated** | Domain expert 2026-05-05 (Q2 = c, defense-in-depth). Prevents both cert-only forgery and payload-only replay. Risk if false: a single layer compromised → cross-tenant access. |
| A-NG3 | Discovery + leader routing is hybrid: client-side topology cache → direct dial to leader → server-side proxy fallback on `LeaderUnavailable`. | **Validated** | Domain expert 2026-05-05 (Q3 = c). Steady-state path is single-hop; fallback covers leader-change windows without forcing a discovery round-trip per retry. Risk if false: every leader change becomes a client-visible failure (the F1 problem from `cluster-harness-followups.md` recurs). |
| A-NG4 | Native POSIX is a strict superset of FUSE POSIX (ADR-013): adds atomic within-shard cross-rename, atomic-create-with-content, lease-based RMW, async batched writes. Cross-shard rename still returns EXDEV (honors I-L8). | **Validated** | Domain expert 2026-05-05 (Q4 = b, Q8 = a). The "atomic cross-rename" claim in the superset is *atomic within-shard cross-directory*, not cross-shard. Risk if false: implementation drift between FUSE and native, or accidentally introducing a cross-shard transaction (violates I-L8 / ADR-026). |
| A-NG5 | Streaming threshold = inline-threshold (default 8 KiB, ADR-006); per-stream cap = 64 MiB. Above the cap, clients use multipart-equivalent fan-out. Object writes commit-on-close (entire stream visible only after `CommitStream` succeeds); POSIX writes against an open handle become visible after `Fsync` succeeds (partial-visible). | **Validated** | Domain expert 2026-05-05 (Q5 = yes). Matches S3 (commit-on-close) and POSIX (partial-visible-on-fsync) consumer expectations. Risk if false: clients see surprising semantics that don't match their existing protocol mental model. |
| A-NG6 | Per-call control fields on native requests are: `workflow_ref` (ADR-020/021 attribution), `cache_hint` (force_revalidate / skip_cache / pin_after_read), `conditional` (if_match / if_none_match / version_id), `idempotency_key` (≤64 B opaque, dedup window 5 min). All four are per-call. The protocol carries no per-connection session state. POSIX inode handles (necessary for I-NG3 fsync semantics) are encoded in opaque, server-signed *handle tokens* returned at open time and presented on every subsequent op; the token carries the open-time mode (e.g., the `crypto_boundary` mode of the namespace at open time, see I-NG6b) so server-side state remains nil. | **Validated** (with F-H1 amendment) | Domain expert 2026-05-05 (Q6 = agreed). Stateless protocol simplifies retries, leader-change handoff, and the future federation case. The handle-token mechanism resolves F-H1 (gate-0 adversary): I-NG6 needs to express "existing handles see the mode they opened under" without server-side per-handle state. The token-with-baked-in-mode achieves this. Risk if false: a session-scoped option (e.g., session-level workflow_ref) re-introduces per-connection state and complicates leader-change failover. Workflow_ref policy: required when tenant policy mandates per ADR-020 (`workflow_ref_required_for_writes = true`); default-when-absent is the literal token `unattributed` (which audit logs surface verbatim — operators / auditors can flag tenants with high `unattributed` counts). Idempotency dedup is workflow_ref-blind: dedup is keyed on `(tenant_id, namespace_id, idempotency_key)` only — a retry with a different `workflow_ref` but the same key is treated as the duplicate of the original (and audited under the original `workflow_ref`). |
| A-NG7 | Encryption boundary is hybrid: server-decrypts by default (`crypto_boundary = ServerOnly`); a per-namespace flag `crypto_boundary = TrustedCompute` opts into client-side decrypt for "trusted compute pool" deployments where the client process is inside the security perimeter. Client-decrypt unlocks GPU-direct + zero-copy paths. **Setting `crypto_boundary = TrustedCompute` requires the namespace to also declare `crypto_shred_policy = best_effort`** — operators acknowledge in writing that a tenant-issued crypto-shred cannot retroactively revoke DEKs already fetched into long-running client process RAM (resolves F-C1). The configuration is rejected if one is set without the other. | **Validated** (with F-C1 amendment) | Domain expert 2026-05-05 (Q7 = c). HPC deployments where compute nodes are tenant-allocated tend to satisfy the trust assumption (cf. A-CC1); SaaS multi-tenant deployments don't. The dual-flag requirement makes the policy degradation explicit and operator-acknowledged rather than implicit. Risk if false: forcing one mode loses either security (always client-decrypt) or performance (always server-decrypt). |
| A-NG8 | Audit attribution for native ops uses the cert SAN URI verbatim as the `principal` field. Existing audit pipeline (ADR-009) auto-fires because the gateway data endpoint dispatches into the same `GatewayOps` trait that S3/NFS/FUSE use; no new audit wiring is needed. | **Validated** | Domain expert 2026-05-05 (Q9 = a). SAN-binding is forgery-resistant. Future ADR (043+) may add per-cert workload identity (SPIFFE workload selectors) for finer attribution. Risk if false: enterprise compliance audits demanding per-human attribution are not satisfied by SAN-URI alone — operators must use SPIFFE / per-job certs. |
| A-NG9 | The data-path gRPC server (port 9100) is the right home for `GatewayDataService`, sharing the existing mTLS, flow-control window (16 MiB stream / 32 MiB connection), and SAN-role interceptor with `ControlService`, `KeyManagerService`, etc. No new port. | **Accepted (risk)** | Reduces operational surface (one TLS cert, one firewall rule). Risk: if `GatewayDataService` traffic dominates the data port, it could starve `LogService` / `KeyManagerService` heartbeats. Mitigated by the shared HTTP/2 flow-control windows and tonic's per-service queues; revisit if production observability shows starvation. |
| A-NG10 | The streaming-write `idempotency_key` dedup window is 5 minutes, **Raft-replicated as a side-effect of the apply phase**: when a write commits, its `(tenant_id, namespace_id, idempotency_key, response_summary)` row lands in a TTL-bounded redb table on every voter. Subsequent retries within the window — including those that arrive after a leader change — read the dedup row from the new leader's local replica and return the original outcome. Outside the window, retried writes are not deduplicated and may double-apply. | **Validated** (with F-H2 amendment) | 5 min covers typical TCP/HTTP retry windows. Resolves F-H2: leader-change-mid-stream retries (F-NG3) commit exactly once because the dedup state is replicated, not leader-local. Cost is a single small redb row per accepted write — well below the cost of a doubled Raft round-trip. If clients retry beyond 5 min, they must use conditional ops (`if_none_match`) for safety. Risk: extends per-voter memory + redb footprint by the dedup window; bounded by per-tenant rate limits. |
| A-NG11 | Performance targets (asymmetric, post in-process floor measurement 2026-05-05): native object-flavored 64 KiB **GET** sustains **≥80 k op/s** per node on the local profile harness, **≥50 k op/s** under multi-instance-on-one-host with R-3. Native object-flavored 64 KiB **PUT** sustains **≥14 k op/s** per node (the in-process PUT floor of 20 k × the 0.7 gRPC tax rule); higher PUT throughput requires a separate gateway-internal-write-path ADR (composition store hot path, AEAD seal cost, chunk-id HMAC). Non-target: matching WekaFS's 150 k op/s without DPDK/SPDK kernel bypass. | **Validated** (post-floor-measurement) | The in-process gateway floor was measured 2026-05-05 with `kiseki-profile --protocol in-process`: get-heavy 114 995 op/s, put-heavy 20 089 op/s. The asymmetric floor reflects the distinct hot paths — GET path is read-shaped (composition lookup + chunk fetch + decrypt) and limited by HTTP framing in the current S3 path; PUT path is gateway-internal-bound (composition write + chunk write + AEAD seal + HMAC). ADR-042's native gRPC can close the protocol-layer gap on GET (115 k floor → 80 k target = 0.7 × ratio; today S3 GET is at 14.6 k → ~5.5× headroom). PUT path requires either ADR-042-shaped scope = ≥14 k or a precursor ADR addressing the write-internal cost. The 80 k GET target and 14 k PUT target are now falsifiable, not aspirational. |
| A-NG12 | Lease-based exclusive writes (I-NG10) attach a monotonically-increasing 64-bit *fencing token* to every write issued under the lease. The server rejects any write whose token is older than the lease's current token (or any other lease's token if the lease was revoked + re-acquired). Resolves the partition-heal split-brain in F-NG4: an old holder whose lease has been re-granted to a new holder receives `LeaseFenced` on its next write regardless of whether it observed the expiry. | **Validated** (with F-H4 amendment) | Pattern from Lamport's fencing-tokens. Combined with the lease TTL (I-NG10), it makes lease-based exclusivity safe under partition. The token is also threaded into the audit event so operators can trace which holder issued each write. Risk if false: split-brain writes from a partitioned old holder are silently accepted; the named-handle "exclusive" guarantee is broken. |
| A-NG13 | Native gRPC responses carry a `topology_version` value in the trailing metadata. Native clients compare the server-supplied version against their cached version on every response and refresh the topology cache when the values disagree. This is push-based invalidation: leader-change thrash is bounded to one extra round-trip rather than the I-NG8 TTL window. The TTL refresh remains a safety net. | **Validated** (with F-M3 amendment) | Same mechanism as etcd's `Cluster::version` and ZooKeeper's `czxid`. Cost is 8 bytes per response. Risk if false: clients see up to 30 s of LeaderUnavailable thrash on every leader change; not a correctness issue but visible to callers as latency outliers. |
| A-NG14 | Concurrent in-flight streaming writes per tenant are bounded by a server-enforced cap (default 256 streams; configurable per tenant via control plane). Excess `OpenStream` requests are rejected with `ResourceExhausted` at the proto-handler boundary before any server-side staging buffer is allocated. | **Validated** (with F-H6 amendment) | Resolves F-H6 (resource exhaustion via concurrent-stream flood). 256 streams × 64 MiB cap = 16 GiB worst-case per-tenant in-flight bytes; tunable per tenant. Risk if false: a malicious or buggy tenant exhausts server RAM. |
| A-NG15 | Native client maintains one tonic Channel per *node it currently believes hosts at least one shard leader for namespaces the client cares about*. The channel is reused for HTTP/2 multiplexing across all such shards. The channel is closed when the client's topology cache no longer has any leader entries pointing at that node (idle drop-out).
