## Finding S1: Stale-leader retry cascade has no enforcement point

**Severity**: High
**Category**: Correctness > Failure cascades
**Location**: `docs/decisions/adr/008-native-client-discovery.md`
rev 2 §"Failure modes / mitigation" — currently text-only.
**Spec reference**: ADR-008 rev 2 §"Failure modes / mitigation"
(2-hop cap).

**Description**: rev 2 says: "Cap retries at **2 hops**; on cap,
propagate `LeaderUnavailable` to the caller." Today this lives only
in prose. There's no `MAX_LEADER_REDIRECT_HOPS` constant in
`kiseki-client::native` and no per-request hop counter on the
request-scoped state.

**Evidence**: `crates/kiseki-client/src/native/client.rs` has no
`hops_remaining` field on `NativeClient` and no plumbing through
the (still-unbuilt) gRPC retry path. A buggy implementer could
write a `while !committed { dial(leader); retry }` loop that
cascades to OOM or wall-clock starvation under sustained churn.

**Suggested resolution**: implementer step adds
`pub const MAX_LEADER_REDIRECT_HOPS: u8 = 2;` next to
`SEED_CONNECT_TIMEOUT` in `crates/kiseki-client/src/native/client.rs`
and threads a `hops_remaining: u8` counter through whatever retry
helper wraps the gRPC call. On cap → return
`NativeClientError::Rpc(Status::unavailable("LeaderUnavailable
after 2 hops"))`. S3 path: the gateway issues 307 with `Retry-After`
header; the *client* (curl, AWS SDK) enforces redirect count via
the existing `--max-redirs 3` convention from the perf-suite bench.
Server-side 307 emission does NOT track hop count (stateless) —
this is correctly a client concern.

**Test plan**: unit test in `topology_cache` simulates a 3-leader
ring where every cache entry redirects to the next; asserts the
RPC bottoms out with `LeaderUnavailable` after 2 hops, not 3.

## Finding S2: Bootstrap seed fall-through is stubbed, not implemented

**Severity**: High
**Category**: Robustness > Resource exhaustion (silent
single-seed fallback when seeds[1..] are configured)
**Location**: `crates/kiseki-client/src/native/client.rs`
`connect_with_seeds` body.
**Spec reference**: ADR-008 rev 2 §"Bootstrap protocol".

**Description**: The architect-step stub of `connect_with_seeds`
only dials `seeds[0]`. If the first seed is down, the call fails —
operator-visible behavior is identical to rev 1's single-seed
`connect()`. This is intentionally left for the implementer step,
but the stub MUST be replaced before any consumer (FUSE, FFI,
Python wrapper) advertises multi-seed support, else clients
silently behave as single-seed even though they pass three seeds.

**Evidence**: `client.rs` body comment:
`// STUB — implementer step replaces the single-seed body with a
proper fall-through loop. Today, the first seed is the only
attempt; behavior matches rev-1.`

**Suggested resolution**: implementer step replaces the stub with:

```rust
let mut last_err = None;
for seed in seeds {
    let url = …;
    let endpoint = Endpoint::from_shared(url)?
        .tcp_nodelay(true)
        .timeout(Duration::from_secs(30))
        .connect_timeout(SEED_CONNECT_TIMEOUT);
    match endpoint.connect().await {
        Ok(channel) => return Ok(Self { … }),
        Err(e) => {
            tracing::warn!(seed, error = %e,
                "native client: seed unreachable, falling through");
            last_err = Some(e);
        }
    }
}
Err(NativeClientError::Connect(format!(
    "all seeds unreachable: {last_err:?}")))
```

**Test plan**: integration test boots a single-node server and
calls `connect_with_seeds(&[unreachable_addr, server_addr])`;
asserts the call succeeds with `topology.snapshot()` populated
from the second seed.

## Finding S3: 307 redirect must preserve request scheme (HTTP vs HTTPS)

**Severity**: High
**Category**: Security > Trust boundaries (TLS downgrade on
redirect)
**Location**: `crates/kiseki-gateway/src/s3_server.rs`
`S3State.peer_s3_addrs` — currently stores `host:port` strings.
**Spec reference**: ADR-008 rev 2 §"Wire shape" — `leader_data_addr`
is documented as `host:port`; the S3 redirect Location field
needs the scheme prefix.

**Description**: AWS S3 SDKs follow 307 redirects but a redirect
from `https://node-a/...` → `http://node-b/...` is a TLS
downgrade. The peer map carries no scheme — if the implementer
hardcodes `format!("http://{host}:9000{path}")` in the Location
header, mTLS-deployed clusters silently issue plaintext
redirects.

**Evidence**: existing `cluster_info` handler synthesizes peer
S3 addrs as plain `"host:9000"`. The Location URL has to be
built at request time from the *current* request's scheme.

**Suggested resolution**: implementer step builds the redirect
Location URL from:

1. The current request's URI scheme (`http` or `https`), obtained
   via `axum::extract::OriginalUri` or the connection's
   `tls_present()` indicator.
2. The peer's `host:port` from `S3State.peer_s3_addrs`.
3. The original path + query string from the request URI.

```rust
let scheme = if request_is_tls { "https" } else { "http" };
let location = format!("{scheme}://{peer_host_port}{path_and_query}");
```

**Test plan**: unit test in `s3_server.rs` confirms that a TLS
request (via a synthesized `https://` request URI) produces a
`Location: https://...` header, and a plain request produces
`Location: http://...`.

## Finding S4: Topology cache version=0 on HTTP bootstrap risks
                overwriting a fresh gRPC update

**Severity**: High
**Category**: Correctness > Concurrency (overlapping refresh
sources)
**Location**: `crates/kiseki-client/src/native/topology_cache.rs`
`snapshot_from_cluster_info()` — architect stub returns
`Snapshot::default()` (version 0).
**Spec reference**: ADR-008 rev 2 §"Bootstrap protocol" + ADR-042
§4 "Consistency model".

**Description**: The TopologyCache version is the steady-state
synchronization primitive — every RPC response trailer carries
the latest authoritative version. `TopologyCache::replace()`
writes the snapshot then bumps `version` atomically; readers
that observe a higher version expect the matching snapshot.

If the HTTP bootstrap produces version=0 and is applied AFTER
a gRPC `GetTopology` returns version=42, the cache regresses to
version=0 with the HTTP snapshot's contents.

The architect-step stub `snapshot_from_cluster_info()` returns
`Snapshot::default()` — version 0. Without a synthetic version
or an explicit "only-if-newer" guard, the cache can regress.

**Evidence**: `topology_cache.rs::replace()` unconditionally
writes the new snapshot and stores the new version. No `>` check.

**Suggested resolution**: implementer step uses **one of**:

(a) **Conditional replace**: add
`fn replace_if_newer(&self, snap: Snapshot) -> bool` that only
overwrites when `snap.version > self.current_version()`. HTTP
bootstrap path uses this; gRPC steady-state uses the
unconditional `replace()`. Returns `false` to signal the caller
that the new snapshot was rejected.

(b) **Synthetic HTTP version**: define `HTTP_BOOTSTRAP_VERSION =
u64::MAX / 2` (a value far above any real Raft version but
predictable) — HTTP bootstrap stamps this, gRPC overwrites with
the real version on first response. Less defensible (loses the
ability to detect a missed gRPC poll), so prefer (a).

The plan calls option (a) the right shape.

**Test plan**: unit test in `topology_cache` that:
1. `replace(snap{version=42})` — cache version = 42.
2. `replace_if_newer(snap_from_http{version=0})` — returns `false`,
   cache version stays 42.
3. `replace(snap{version=43})` — unconditional path bumps to 43.

## Finding S5: `Retry-After` jitter range needs a concrete RNG choice

**Severity**: Medium
**Category**: Robustness > Resource exhaustion (307-storm
amplification)
**Location**: `crates/kiseki-gateway/src/s3_server.rs` (no code
yet — architect stubbed the field, not the emission).
**Spec reference**: ADR-008 rev 2 §"Failure modes / mitigation"
+ specs/implementation/write-routing-posture.md §4 finding 5.

**Description**: rev 2 prescribes `Retry-After: 0-50ms` jitter
on the 307 response. The implementer step needs to pick:

1. An RNG source. `rand::random()` is fine but pulls in `rand`
   on the hot path (the s3_server already uses `prometheus` —
   `rand` is a separate crate). Check Cargo.toml.
2. A jitter unit. RFC 9110 §10.2.3 says `Retry-After` is
   delta-seconds — integer seconds only. **0-50ms is not
   expressible as an RFC-compliant Retry-After header.**

**Evidence**: HTTP `Retry-After` accepts `delta-seconds` or
`HTTP-date`. Sub-second granularity is not in the spec. Clients
(curl, AWS SDK) MAY interpret `Retry-After: 0` as "retry
immediately", which gives no jitter at all.

**Suggested resolution**: implementer step picks **one of**:

(a) **Drop the header**: don't emit `Retry-After`. Rely on the
client SDK's default exponential backoff between retries. This
is what AWS S3 does for 5xx responses without `Retry-After`.

(b) **Emit `Retry-After: 1`** (1 second integer): bounded but
coarse. Acceptable for the perf-cluster bench but loses the
sub-second jitter goal.

(c) **Emit a custom `X-Kiseki-Retry-After-Ms: 0-50`** alongside
`Retry-After: 1`. AWS SDKs ignore the custom header; curl +
the perf bench's own retry helper read it. Belt-and-braces.

Recommend (a) — simplest, RFC-compliant, lets the bench harness's
own retry policy carry the jitter. The 307-storm risk is
mitigated mainly by the topology-cache refresh on the *client*
side after one redirect, which cuts the storm window to one
round-trip per client. Server-side jitter is a defense-in-depth
that the wire protocol doesn't allow at sub-second granularity
anyway.

**Test plan**: unit test confirms the 307 response carries NO
`Retry-After` header (under option (a)); a follow-up integration
test confirms the perf-bench's retry policy converges within
3 redirects.

## Finding S6: GET requests to non-leader nodes should NOT 307

**Severity**: Medium
**Category**: Correctness > Specification compliance
**Location**: implementer step — the 307 emission path.
**Spec reference**: ADR-040 §D7 + I-2 (read path serves any node
with composition state); ADR-042 §4 / ADR-008 rev 2 specify 307 for
write redirects only.

**Description**: A GET to a non-leader node SHOULD succeed:
followers maintain composition state via the hydrator (ADR-040
§D6.3). The 307 redirect mechanism is for *writes* (PUT, DELETE,
POST multipart). If the implementer wires the 307 path on every
`LeaderUnavailable` (including GETs that didn't need a leader at
all), the gateway throws away the very feature ADR-040 hydrator
gives us.

**Evidence**: `s3_server.rs::get_object` calls
`gateway.get_object(...)`. Today the read path can return
`ServiceUnavailable(...)` when the hydrator halts (existing 503
behavior). It should NOT trip `LeaderUnavailable` because the
read path doesn't go through Raft — but a future implementer
might tile the 307 mapping across all error variants and break
this contract.

**Suggested resolution**: implementer step's 307 emission must
be **method-gated**: only PUT / POST / DELETE / PATCH map
`GatewayError::LeaderUnavailable` → 307. GET / HEAD / LIST map
the same error → 503 + `Retry-After` (matching the existing
ServiceUnavailable path), since the read path SHOULD succeed
locally and a `LeaderUnavailable` from a GET is a bug worth
surfacing.

**Test plan**: unit test in `s3_server.rs` confirms:
1. PUT against `LeaderUnavailable` → 307 + Location.
2. GET against `LeaderUnavailable` → 503 + Retry-After.

## Finding S7: Cross-tenant shard map exposure on /cluster/info is
                accepted-by-design but not documented in `enforcement-map`

**Severity**: Low (already escalated in ADR-008 rev 2 §"Authorization")
**Category**: Security > Tenant isolation
**Location**: `specs/architecture/enforcement-map.md` (if it
exists).
**Spec reference**: ADR-008 rev 2 §"Authorization for
/cluster/info".

**Description**: rev 2 explicitly punts per-tenant filtering on
the HTTP bootstrap endpoint to network-boundary gating of the
metrics port (9090). For multi-tenant production deploys this
shifts the burden from the gateway to the cluster operator.
ADR-042 §4 "GetTopology contract" enforces per-tenant filtering
on the gRPC follow-up. The contrast (HTTP unauthenticated vs.
gRPC authenticated) should appear in the enforcement-map so
operators don't assume HTTP bootstrap is tenant-safe.

**Evidence**: `docs/decisions/adr/008-native-client-discovery.md`
rev 2 §"Authorization" makes the call explicitly, but the
project's `enforcement-map.md` (if present) doesn't reflect it.

**Suggested resolution**: implementer / integrator step appends a
row to `specs/architecture/enforcement-map.md` (or
`specs/findings/2026-05-15-step-c-gate1.md` if no enforcement-map
exists) cross-referencing ADR-008 rev 2 §"Authorization" so the
operational expectation is one grep away.

**Test plan**: none — design-level finding, no code change.

## Finding S8: `kiseki_native_topology_stale_leader_redirects_total`
                lacks a tenant label

**Severity**: Low
**Category**: Robustness > Observability gaps
**Location**: `crates/kiseki-server/src/metrics.rs`
`stale_leader_redirects_total: IntCounterVec` — labels
`&["protocol"]` only.
**Spec reference**: ADR-008 rev 2 §"Observability" — specifies
`{protocol, tenant}` labels.

**Description**: rev 2 prescribes `kiseki_native_topology_stale_
leader_redirects_total{protocol, tenant}` so per-tenant
churn alerts can target the noisy tenant. The architect-step
stub registers only the `protocol` label, dropping `tenant`.

**Evidence**: `metrics.rs::stale_leader_redirects_total` is
`IntCounterVec::new(Opts::new(...), &["protocol"])`.

**Suggested resolution**: implementer step changes label set to
`&["protocol", "tenant"]`. The S3 emission site has access to
`state.fallback_tenant` (or the SigV4-resolved tenant in
multi-tenant mode); the native path has the SAN-derived tenant.
Both feed the `tenant` label as the tenant UUID's string form.

**Test plan**: confirm the metric label set in the
metrics-encode test (`/metrics` body contains
`stale_leader_redirects_total{protocol="s3",tenant="..."}`).
