### §2 — Invariant preservation

**I-L2 (ack only after Raft commit) — PASS.** `kiseki-log/src/raft/openraft_store.rs:408-418` shows `append_delta_with_forwarding` awaits `self.raft.client_write(cmd).await` BEFORE pattern-matching on `LogResponse::Appended(seq)`. There is no early-Ok branch. `mem_gateway::write_impl` at line 2235 only returns `Ok(WriteResponse)` after `emit_chunk_and_delta_with_forwarding` resolves to `Ok(seq)`; on `Err(ForwardToLeader)` the composition row is rolled back (`self.compositions.delete(comp_id).ok()` line 2282) and the error propagates. `ServerImpl::put_object` (line 492-539) only emits the proxy-fallback `Status::unavailable` on the error branch and only emits success after `Ok(r)` (line 494). No code path returns `Ok` before the leader's commit.

**I-NG5 (idempotency-key byte-preserve through proxy) — DEFERRED, MED.** `crates/kiseki-gateway/src/ops.rs:37-62` defines `WriteRequest` with no `idempotency_key` field. The native server validates `cf.idempotency_key` at `server.rs:467` and then constructs `WriteRequest` at line 480 WITHOUT the key. When the wire-level proxy dial lands, the implementer MUST either (a) thread `idempotency_key` through `WriteRequest`, or (b) re-issue the original `PutObjectRequest` (carrying `ControlFields.idempotency_key`) as the proxy hop's outbound RPC. The plan §3 step A bullet 2 promises "re-issue the RPC with the *original* `ControlFields` (idempotency_key dedups per ADR-042 §6)" — option (b) preserves the bytes; option (a) requires routing through `WriteRequest`. The current code does neither. The BDD `@deferred-feature` scenario "Server-side proxy fallback — proxying node fails mid-proxy" (lines 184-190) asserts "the server returns the original outcome (idempotency dedup via I-NG5 + A-NG10) and the write commits exactly once" — this assertion will fail without the key-preservation fix.

**Recommendation**: the wire-level-proxy implementer adds `idempotency_key: Option<Vec<u8>>` to `WriteRequest` (or re-issues the typed PutObjectRequest direct). Flag for the integrator and for the follow-up implementer.

**I-NG13 (topology refresh on version mismatch) — PASS.** `kiseki-client/src/native/topology_cache.rs:128-135` shows `replace_if_newer` returns `false` when `snap.version <= self.current_version()`; only strict-greater triggers `self.replace(snap)`. Unit tests at lines 769-802 cover (a) equal version rejected, (b) stale (version=0) rejected, (c) strictly greater accepted, (d) empty-cache populated by any non-zero version. Multi-case, falsifiable.

**I-NG1 (SAN-vs-payload tenant check on proxy hop) — DEFERRED, MED.** The finding doc `specs/findings/2026-05-15-leader-forwarding-posture.md:109-115` (§ M2) explicitly identifies the cross-tenant SAN check at the proxy boundary and prescribes a `forwarded_from_node` field in `ControlFields` (or metadata `kiseki-forwarded-from-node`) so the leader's audit log records both the originating tenant AND the forwarding node. This is unimplemented today (wire-level proxy deferred). The native server's `enforce_san_payload_tenant_match` (`server.rs:469`) currently does NOT have a forwarded-from-node bypass / audit path. When the wire-level proxy lands, the leader's audit record MUST carry `forwarded_from_node = source_node_id`.

**Recommendation**: integrator + follow-up implementer add the audit-trail field per the finding doc; current `@deferred-feature` BDD scenarios should be extended with a "forwarded-from-node recorded" Then assertion before un-deferring.

**4c. `kiseki_native_topology_stale_leader_redirects_total` — FAIL, CRITICAL.**
- Registry (`metrics.rs:319-326`): `&["protocol"]` — ONE label.
- Plan (§3 Step C, line 117): "Add metric `kiseki_native_topology_stale_leader_redirects_total` per ADR-042 §4."
- ADR-008 rev 2 §"Observability": metric labels `(protocol, tenant)`.
- `s3_server.rs:299` (the call site inside `leader_unavailable_response`): `c.with_label_values(&["s3", "unknown"]).inc();` — TWO values.
- The unit test (`s3_server.rs:1935-1958`) builds a LOCAL counter with `&["protocol", "tenant"]` (2 labels) so the test passes against a different counter shape than the one registered in the server.

When the integrator wires the real `kiseki_native_topology_stale_leader_redirects_total` into `leader_unavailable_response` (passing the registered counter into the call), `prometheus::IntCounterVec::with_label_values(&["s3", "unknown"])` will panic because the values-vec length (2) does not match the variable-labels arity (1). This is a runtime panic on every 307 emission — every S3 PUT/POST/DELETE/PATCH against `LeaderUnavailable` would crash the request handler.

**Recommendation (small fix, can land now without integrator territory)**: bump the registered metric to `&["protocol", "tenant"]` to match the call site and ADR-008 rev 2. Two-line fix in `metrics.rs`. I am applying this fix as a one-line edit in a follow-up commit (see below).

**4d. S3 307 method gating — PASS.** `s3_server.rs:275-284`: `let is_write = matches!(*method, Method::PUT | Method::POST | Method::DELETE | Method::PATCH); if !is_write { return service_unavailable_with_retry_after(); }`. GET / HEAD / LIST / OPTIONS fall through to 503. Test `leader_unavailable_get_returns_503_not_307` (line 1876) confirms.

**4e. `/cluster/info` shape — PASS.** `web/api.rs:74-90` defines `ShardInfoJson` with `shard_id, namespace_id, leader_id, leader_data_addr, range_start, range_end`. Plan asked for 5 fields; impl ships 6 (added `namespace_id`, which the discovery client already consumes per `discovery.rs:381`). No regression.
